# Практический процесс перевода видео AKB48

Адаптировано 2026-11-01 из локального рабочего описания
`VIDEO_TRANSLATION_WORKFLOW.md`. Здесь сохранены полезные приёмы обработки
выпусков, но команды используют относительные пути и инструменты публичного
репозитория. Полный цикл включает программную обработку и языковую/визуальную
работу редактора или агента; единой команды автоматического качественного
перевода здесь нет.

## 1. Что установлено и что выполняется отдельно

Обязательны доступ к Codex или другому подходящему агенту, исходное видео,
Python и FFmpeg/FFprobe. Проверочные скрипты skill используют стандартную
библиотеку Python. Для ASS нужна сборка FFmpeg с libass и шрифтами выбранного
языка. Платный API перевода не является обязательной зависимостью скриптов;
доступ к самому агенту и его модели настраивается отдельно.

Дополнительное распознавание выполняется, например, локальным faster-whisper.
Он не устанавливается вместе со skill. [Инструкция установки и запуска](../.agents/skills/akb48-video-subtitles/references/transcription.md)
описывает CPU/int8, отдельное окружение и японскую расшифровку с временными
метками. WSL и GPU необязательны. Распознавание не переводит речь на целевой
язык в описанном процессе и не устанавливает, кому принадлежит реплика.

Для выпуска 1080p продолжительностью 20–40 минут ориентир — от 8 ГБ RAM и
современного четырёхъядерного CPU; комфортнее 16 ГБ и 6–8 ядер при локальном
ASR. Около 10 ГБ свободного места — начальная оценка для исходника, промежуточных
файлов и результата. Размер модели, 4K, высокий битрейт и резервные копии могут
потребовать больше. Это не замер производительности данного репозитория.

## 2. Создать папку выпуска

Следующие команды выполняются из корня клонированного репозитория. Во всех
примерах `episodes/demo` — локальная рабочая папка; видео и переводы не следует
добавлять в публичный Git-коммит.

```sh
python .agents/skills/akb48-video-subtitles/scripts/check_environment.py --require-ass
python .agents/skills/akb48-video-subtitles/scripts/init_project.py --project episodes/demo --episode-id demo --locale ru
```

Инициализатор создаёт `episode.json` и папки `source/`, `work/chunks/`,
`output/`, `reports/`, отказываясь перезаписывать непустую папку. В манифесте
указать источник, длительность, разрешение, требуемые форматы и пути файлов.
Относительные пути в нём считаются от папки выпуска. Проверки сами не скачивают
видео, не распознают речь и не собирают перевод.

## 3. Выбрать источник и японскую дорожку

Предпочтителен предоставленный локальный исходник. Зафиксировать название,
URL/происхождение, длительность, точную частоту кадров, разрешение и языки
аудиодорожек:

```sh
python .agents/skills/akb48-video-subtitles/scripts/probe_media.py episodes/demo/source/original.mp4 --json
```

Если требуется разрешённая загрузка через yt-dlp, сначала отдельно установить
его и проверить доступные дорожки. Номера форматов и порядок аудиопотоков не
постоянны. Не копировать идентификатор формата из другого выпуска: вместо
японской дорожки можно получить автоматический дубляж. Не публиковать cookies,
временные прямые URL из метаданных или учётные данные.

В исходном локальном процессе использовались отдельные загрузчики по диапазонам
и скрипты объединения. Они не входят в этот репозиторий и не требуются для
работы с уже готовым локальным видео.

## 4. Собрать японский текст и контекст

Проверить, существуют ли авторские японские субтитры. Автосубтитры YouTube и
Whisper — черновые источники, которые могут ошибаться, особенно при смехе,
числах, пении и одновременной речи. Независимое распознавание полезно и при
наличии автосубтитров: сравнивать разногласия с аудио, а не принимать совпадение
двух ASR за доказательство.

Перед переводом сохранить состав выпуска, роли ведущих, обращения, структуру
игр и словарь. Использовать проверенный словарь конкретного выпуска; встроенные
словари не являются полным актуальным составом группы. Статусы и источники
имён важнее наличия строки в CSV. Сведения из предыдущей серии помогают понять
контекст, но не доказывают личность текущего говорящего.

```sh
python .agents/skills/akb48-video-subtitles/scripts/lookup_member.py --locale ru "武藤小麟"
python .agents/skills/akb48-video-subtitles/scripts/lookup_term.py --locale ru "選抜"
```

Названия песен сохранять в проверенном латинском/romaji написании по
[политике названий](../.agents/skills/akb48-video-subtitles/glossaries/songs/README.md).
Перевод текста песни — отдельная задача.

## 5. Перевести с сохранением связи с источником

Сохранить японские реплики и переводы в JSON по
[контракту стабильных ID](../.agents/skills/akb48-video-subtitles/references/translation-protocol.md).
Рабочие блоки обычно содержат 40–60 реплик, но граница сцены может требовать
более короткого блока. В каждом блоке сохранить ID, их порядок и непустой
перевод. Это рабочие единицы перевода, а не окончательные границы отображения.

Пример проверки одного блока — пути должны указывать на реально подготовленные
файлы, команды не создают их автоматически:

```sh
python .agents/skills/akb48-video-subtitles/scripts/check_translation.py --input episodes/demo/work/chunks/source.json --translated episodes/demo/work/chunks/translated.json --target-lang ru --json
```

Сверять имена, субъект действия, отрицания, числа, шутки и обращения. Не
восстанавливать неразборчивое содержательное место догадкой. Русский перевод
строить по японскому источнику, не через случайный английский автоперевод.
Автоматические проверки не доказывают точность смысла.

## 6. Отдельно разметить говорящих

Смены голосов устанавливаются по аудио и проверяемому контексту. Крупный план
человека сам по себе не доказывает авторство. Если личность не установлена,
использовать нейтральную роль или убрать имя. Не скрывать несколько смен
говорящего в одной строке с цепочкой тире.

Обычный вариант — последовательные события с именем. Для очень короткого
обмена допустимы две отдельные подписанные строки. Цвет — дополнительный
признак; видимое имя остаётся основным. Удлинение времени чтения не должно
переносить реплику на ответ другого участника.

В локальных выпусках часть границ была уточнена вручную, часть предварительно
оценивалась по длине текста. Это не автоматическая диаризация и не forced
alignment. Такие границы требуют проверки и честного указания ограничений.

## 7. Прочитать экранные надписи по всему ролику

Составить отдельный список заголовков, правил, карточек, результатов,
редакторских подписей и объявлений. OCR и выборка кадров помогают, но короткая
надпись может появиться между выбранными кадрами. Для полноты нужен просмотр
переходов и уточнение начала/конца каждой важной вставки.

Пример выборки (папку `frames` создать заранее; возможны многие сотни файлов):

```sh
ffmpeg -nostdin -i episodes/demo/source/original.mp4 -vf "fps=1/4,scale=1280:-2" -q:v 3 episodes/demo/frames/frame-%05d.jpg
```

Для каждой вставки сохранить время, перевод и область кадра. Координаты относятся
к конкретному разрешению. Типовое рабочее событие может иметь `start_ms`,
`end_ms`, `text`, `kind`, `x`, `y`, `width`, `height`. Это рекомендуемая рабочая
разметка, не входная схема готового сборщика в этом репозитории.

Разделять речь и надписи даже при совпадении текста. Логотипы и повторяющиеся
бейджи не обязательно заменять на каждом кадре; фиксировать, что осталось
видимым. Не заявлять полную локализацию по редкой выборке кадров.

## 8. Тайминг и оформление

Проверять реальную скорость чтения, строки, паузы и смены говорящего. В русском
профиле 700 мс — нижний порог для проверки, 900 мс — предпочтительный ориентир.
Около 23 знаков/с — флаг внимания, не универсальная норма для всех языков.
Имена и пробелы тоже создают нагрузку чтения. Короткие реакции и парные реплики
требуют индивидуального решения.

В компактном оформлении последних локальных выпусков использовались следующие
параметры для 1920×1080. Это описание примера, не обязательные настройки skill:

| Элемент | Пример |
|---|---|
| Нижняя плашка | x=110, ширина 1700, нижняя граница y=1050 (отступ 30 px) |
| Высота | 82 px для строки, 128 px для двух строк |
| Основной текст | 40 px, тёмный, светлая подложка |
| Имя | 26 px, для длинного имени 22 px, тонкий цветной маркер |
| Парный обмен | отдельные подписанные строки, 38/32 px по переносам |
| Верхний заголовок | две компактные полосы, без перекрытия лиц |

На другом шрифте и языке прежнее число символов не гарантирует ширину строки.
Проверять рендер libass: короткий ответ, длинную фразу, длинное имя, парный
обмен и одновременную надпись. Segoe UI из локального процесса не следует
включать в репозиторий; использовать доступный шрифт с нужным покрытием и
проверить подстановку. В готовом MP4 текст уже отрисован.

## 9. Подготовить SRT/ASS и проверить превью

Обычные результаты: `dialogue.ru.srt` для речи, `inscriptions.ru.srt` для
надписей и `subtitles.ru.ass` для совместного оформления. SRT не сохраняет
координаты и цвет. В ASS подложки, именные метки и текст могут законно
перекрываться по времени на разных слоях.

Для проверенной разметки говорящих теперь есть [контракт и сборщик компактного оформления](../.agents/skills/akb48-video-subtitles/references/presentation.md): `build_presentation.py` создаёт SRT/ASS из `work/presentation.json`, а `check_presentation.py` проверяет разметку и соответствие результата. Это сборщик отображения, а не автоматический перевод или диаризация. Локальные
`proof_speech.py`, `make_signs.py`, `build_subtitles.py` и `package.py` из старого
рабочего MD были программами конкретных выпусков; команды их запуска здесь
намеренно не выдаются за устанавливаемые инструменты.

```sh
python .agents/skills/akb48-video-subtitles/scripts/check_srt.py episodes/demo/output/dialogue.ru.srt --profile ru --duration 120
python .agents/skills/akb48-video-subtitles/scripts/check_ass.py episodes/demo/output/subtitles.ru.ass --width 1920 --height 1080 --duration 120
```

Заменить `120` и размеры реальными значениями. Для превью удобно извлекать
кадр из уже вшитого результата. При фильтрации ASS после входного `-ss`
проверять временную шкалу: субтитры рассчитаны на исходное время, а не ноль
отрезанного клипа. Ошибка шкалы может выглядеть как отсутствие субтитров.

## 10. Вшить субтитры

Этот пример выполняется **из папки `episodes/demo/output`**, где лежит ASS.
Относительный путь к ASS избегает дополнительного экранирования диска Windows
внутри фильтра. Имена файлов с апострофами/двоеточиями потребуют отдельного
экранирования. Пример рассчитан на совместимый с MP4 источник и доступный
кодировщик libx264; это CPU-вариант, не обязательное требование к кодировщику.

```sh
ffmpeg -nostdin -i ../source/original.mp4 -map 0:v:0 -map "0:a:0?" -vf ass=subtitles.ru.ass -c:v libx264 -crf 20 -preset medium -pix_fmt yuv420p -c:a copy -movflags +faststart video.ru.tmp.mp4
```

Не задавать другую частоту кадров без цели её изменить. Если первая аудиодорожка
не японская, изменить `-map` после проверки. Если кодек аудио несовместим с MP4,
выбрать подходящий контейнер либо согласовать перекодирование и явно отметить
изменение аудио. Финальный файл сначала создаётся под временным именем.

Аппаратный AMD AMF из локального процесса — вариант конкретной машины, не
переносимая зависимость. Удаление SEI из H.264 тоже было обходом отдельных
источников: оно может удалить важные метаданные и не должно выполняться по
умолчанию, особенно для HDR.

## 11. Техническая, языковая и визуальная приёмка

Указать в `episode.json` реальный путь временного видеорезультата,
`requested_outputs` и `audio_preservation`. Затем из корня репозитория:

```sh
python .agents/skills/akb48-video-subtitles/scripts/run_checks.py --project episodes/demo --require-translation --media-timeout 1800 --json
```

`report.json` содержит фактически выполненные проверки и пропущенные этапы.
Для видео выполняются сравнение метаданных, полное декодирование обоих файлов,
сравнение фактического числа кадров и, если требуется, декодированного аудио.
`compare_audio.py` проверяет PCM s16le; это не доказательство побайтовой
идентичности сжатых аудиопакетов. Пропущенная проверка не считается успешной.

Отдельно проверить смысл, авторство реплик, полноту надписей и реальные кадры.
Статический ASS-анализ не измеряет все реальные переносы и не видит лица.
Прохождение технических проверок не подтверждает качество перевода или права
на публикацию. Тайм-аут задаётся в секундах на файл и при необходимости
увеличивается; один `progress=end` без успешного кода завершения недостаточен.

## 12. Упаковка и новые версии

После проверки сохранить готовое видео, ASS, отдельные SRT, README результата,
использованный словарь, превью и отчёт. По запросу добавить ZIP субтитров;
проверить целостность и совпадение вложенных файлов с текущей ревизией.
Сохранить источник и рабочую разметку локально для исправлений.

При правке сначала сделать резервную копию, пересобрать зависимые ASS/MP4,
заново проверить изменённые результаты и обновить архив/отчёт. Изменение ASS
не меняет уже вшитый MP4. После переименования временного файла обновить пути
в манифесте и отчёте, чтобы ссылки в выдаче указывали на текущий результат.

Исторические числа реплик, кадров и скорости отдельных выпусков не являются
контрактом для нового видео. Публиковать только те материалы, на которые есть
нужное разрешение; рабочие расшифровки и исходные ролики хранить отдельно от
публичного репозитория инструментов.

## Правки после независимого теста

Фоновые песни и концертные песенные вставки по умолчанию не переводятся и не вшиваются. Для исключения нужны явный запрос пользователя, lyrics_policy=requested и запись lyrics_request в episode.json. Названия песен и реплики поверх музыки — отдельные классы. Сохранить сырое ASR и журнал исключённых ID; стабильность ID проверяется для выбранного объёма перевода.

В ASS/видео теперь обязательна work/presentation.json. Нельзя объединять два неизвестных голоса только по близости времени. У парного обмена каждая строка имеет имя/роль; неустановленный автор явно отмечен. Нижняя граница — 30 логических пикселей от края 1080p, то есть 20 px на 720p. Подъём в отдельной сцене задаётся с причиной. Надписи располагаются отдельно от речи и имеют другой визуальный стиль.
